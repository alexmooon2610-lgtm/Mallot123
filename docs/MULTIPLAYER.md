# STEEL TEMPEST — 멀티플레이 설계

작성 2026-11-17 · 대상 버전 **V15.0.0** (멀티 첫 공개). 기틀 단계는 `V15.0.0-alpha.N` 으로 표기한다.

## 1. 정한 것 (사용자 결정 2026-11-17)
| 항목 | 결정 |
|---|---|
| 첫 모드 | **1대1 대전 (PvP)** |
| 최대 인원 | **4명** (처음엔 2명, 구조는 4명까지) |
| 접속 | **방 코드로 친구끼리** (매칭 없음) |
| 서버 | **무료 외부 서비스로 시작** — 접속 중개만 PeerJS 공용 서버, 게임 데이터는 플레이어끼리 직접(P2P) |

## 2. 구조

### 2-1. 연결: 방장 중심 별 모양 (host star)
```
        ┌── 참가자 1
방장 ───┼── 참가자 2        참가자끼리는 직접 연결하지 않는다. 방장이 중계한다.
        └── 참가자 3
```
- 방장이 방을 만들면 6자리 코드가 생긴다. PeerJS 아이디 `steeltempest-<코드>` 를 방장이 쓴다.
- 참가자는 코드를 넣어 그 아이디로 접속한다. 4명까지 받고 넘치면 거절.
- 데이터 길: WebRTC 데이터 채널 (PeerJS). 중개 서버(0.peerjs.com)는 처음 연결할 때만 쓴다.
- **위험**: 일부 회사망 · 이동통신망(대칭형 NAT)에서는 P2P 가 안 뚫린다. 그때는 TURN 중계 서버가 필요하다
  (무료는 거의 없음 — 문제가 실제로 생기면 그때 정한다).

### 2-2. 동기화: 자기 기체는 자기가 계산한다 (owner-authoritative)
**락스텝(같은 입력 → 같은 결과)을 쓰지 않는다.** 이유: 브라우저마다 `Math.sin` · `Math.exp` 결과가 끝자리까지 같다는
보장이 없어 판이 조금씩 갈라진다. 또 입력을 다 모을 때까지 기다려야 해서 지연이 그대로 조작감에 붙는다.

대신:
- **내 기체는 내 컴퓨터가 계산**하고, 초당 20번 상태(위치 · 속도 · 자세 · 추력 · 기어 · 체력)를 보낸다.
- **남의 기체는 받은 상태를 100 ms 늦게 보간**해서 그린다. 받은 게 끊기면 속도로 250 ms 까지 내다본다(외삽).
- 그래서 내 조작은 지연 없이 바로 반응하고, 상대는 약간 과거 모습으로 보인다.

### 2-3. 무장 판정: 맞는 쪽이 판정한다 (victim-authoritative) — 2단계에서 구현
| 대상 | 계산하는 쪽 | 보내는 것 |
|---|---|---|
| 기총 탄 | 쏜 쪽이 탄마다 발사 위치 · 속도를 보낸다 | 받은 쪽은 같은 탄을 날려 **자기 진짜 위치**로 맞았는지 판정 |
| 미사일 | 쏜 쪽이 유도 계산 (상대는 보간된 모습으로 추적) · 상태 전송 | 맞는 쪽이 자기 진짜 위치로 명중 판정 |
| 플레어 · 채프 | 뿌린 쪽 | 기만 성공 여부도 뿌린 쪽이 굴려 보낸다 (미사일 주인은 결과를 받아 유도를 바꾼다) |
| 피해 · 격추 | 맞은 쪽 | `hit` · `kill` 사건을 모두에게 |

맞는 쪽 판정은 "분명히 피했는데 맞았다"가 없다. 대신 쏜 쪽은 맞힌 것 같은데 안 맞을 수 있다 (지연만큼).
친구끼리 하는 게임이라 부정행위 방지는 고려하지 않는다.

### 2-4. 판정 난수
각자 자기 판정(자기 기체가 맞았나, 내 플레어가 속였나)에 자기 `rnd` 를 쓴다. 서로 난수열을 맞출 필요가 없다.
싱글 플레이 경로는 손대지 않는다 — **싱글 회귀 검사 기준값이 그대로여야 한다.**

## 3. 통신 규약 (v1)
모든 메시지는 JSON `{ t: 종류, ... }`. 방장은 참가자 메시지를 다른 참가자에게 그대로 중계한다 (`from` 을 붙여서).

| t | 보내는 쪽 | 내용 |
|---|---|---|
| `hello` | 참가자 → 방장 | `v` 규약 버전 · `build` 게임 버전 |
| `welcome` | 방장 → 참가자 | `slot` 내 자리(0 방장, 1~3) · `players` |
| `reject` | 방장 → 참가자 | `why` (가득 참 · 버전 다름 · 이미 시작) |
| `roster` | 방장 → 모두 | 접속자 목록 |
| `start` | 방장 → 모두 | `mode` · `arena` · 시작 신호 |
| `s` | 모두 | 기체 상태: `slot` · `n` 순번 · `tm` 보낸 쪽 시계(ms) · `p` 위치 · `v` 속도벡터 · `q` 자세 · `thr` · `ab` · `gr` 기어 · `fp` 플랩 · `hp` |
| `ping` / `pong` | 모두 | 왕복 시간 · 시계 차이 추정 |
| `bye` | 모두 | 나감 |
| (2단계) `gun` · `msl` · `mst` · `cm` · `hit` · `kill` · `round` | | 무장 · 판정 · 판 진행 |

- 상태 전송 초당 20번 → 기체 하나 약 200 바이트 × 20 = 4 KB/s. 4명이면 방장 업로드 약 50 KB/s.
- 3초간 아무것도 안 오면 끊긴 것으로 본다.

## 4. 코드 배치
| 파일 | 내용 |
|---|---|
| `05-net.js` | `NET` — 전송 계층(PeerJS · 시험용 relay), 방 만들기/참가, 중계, 핑 · 시계 차이, 끊김 감지. 게임 코드에 의존하지 않는다 |
| `20-mission-versus.js` | `MISSIONS.VERSUS` — 1대1 대전 공역 · 출발 자리 · 상대 기체(원격 개체) 생성 · 상태 송신 · 보간 |
| `91-net-lobby.js` | 메뉴의 MULTI 버튼 → 방 만들기 / 코드로 참가 / 출격 |
| `36-enemy-ai.js` | `aiUpdate` 첫 줄: 원격 개체(`e.net`)는 AI 대신 보간 |
| `30-hitbox-guns.js` | `collide` — 원격 개체와의 공중 충돌은 1단계에서 제외 (2단계에서 맞는 쪽 판정으로) |

PeerJS 라이브러리는 **멀티 메뉴를 열 때만** CDN 에서 불러온다 (싱글은 영향 없음, 오프라인이어도 싱글은 된다).

## 6. 시험
- **두 페이지 시험**(`tools/harness/nettest.py`): 브라우저 페이지 둘을 띄우고, 메시지를 하네스가 직접 날라 준다
  (`?net=relay` 전송). 지연 · 흔들림 · 끊김을 마음대로 넣을 수 있다. 실제 PeerJS 서버는 거치지 않는다.
- 확인하는 것: 연결 · 자리 배정 · 시작 신호 · 서로의 기체가 보간 오차 안에서 같은 곳에 보이는가 · 끊김 감지.
- **싱글 회귀**: 멀티 코드를 넣은 뒤에도 싱글 시나리오 전부 기준값과 프레임 단위 동일.
- 실제 인터넷 연결은 사용자가 두 기기로 시험해야 한다.

### 1단계 시험 결과 (V15.0.0-alpha.1, 2026-11-17)
| 확인 | 결과 |
|---|---|
| 방 만들기 · 코드 참가 · 자리(0 · 1) · 접속자 목록 2명 | 통과 |
| 방장 출격 → 둘 다 VERSUS 시작 | 통과 |
| 서로의 기체가 보인다 | 통과 (25초 동안 47번 확인) |

| 방장 신호가 끊기면 참가자가 알아챔 | 3.05초에 "대전 종료 — 방장과 연결이 끊겼다" |
| 싱글 시나리오 17개 | V14.8.0 기준과 전부 동일 |

**아직 시험 못 한 것**: 실제 PeerJS 서버 · WebRTC 경로 (`peerTransport`). 이 작업 환경에서는 바깥 서버로 가는
브라우저 연결을 열 수 없어서, 두 기기(또는 한 컴퓨터의 브라우저 창 두 개)로 사람이 직접 확인해야 한다.
1. 게임 파일을 두 창(또는 두 기기)에서 연다 → 설정 화면 → **MULTI PLAYER**
2. 한쪽: **방 만들기** → 6자리 코드 · 다른 쪽: 코드 입력 → **참가**
3. 방장 화면에 2명이 보이면 **출격** → 서로 10 km 떨어져 마주 본 채로 시작한다
