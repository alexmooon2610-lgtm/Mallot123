마지막 갱신: 2026-11-18 · 버전 **V15.0.0-alpha.6** (멀티플레이 기틀 + **Su-33 선택** + **무한모드 날씨 · 시간대** + **렌더 자동 점검** + **야간 조명 · 광학 착함 장치** — `docs/MULTIPLAYER.md`) · 저장소 `steel-tempest/` (로컬 git — **원격에 올릴 것**, 3-0절)

이 문서 하나로 프로젝트 전체를 파악할 수 있게 썼다. 코드를 처음 보는 사람이 읽고 바로 이어서

## 1. 게임이 무엇인가

브라우저에서 도는 **항모 공중전 게임**. HTML 파일 하나(14.5 MB)로 돌아가고, 설치도 서버도 필요 없다.
더블클릭하면 그냥 켜진다.

**이야기**: 1999년 12월, 러시아 항공모함 「자랴」(쿠즈네초프급)가 시간 이동 장치 **크로노 코어**를
확보해 태평양으로 나선다. 12월 20일 시공 폭풍에 휩쓸려 **1941년**으로 떨어진다. 플레이어는 MiG-29
조종사로, 과거에서 보급도 지원도 없이 싸우며 원래 시간선으로 돌아갈 길을 찾는다.
2000년 1월 1일 00:00(원래 시간선 기준)이 지나면 코어가 영구 잠긴다(Y2K 잠금) — 이게 캠페인의 제한 시간이다.

**모티브**: C&C 레드얼럿 2, 영화 파이널 카운트다운, 워 썬더, 에이스 컴뱃 시리즈.
조작감과 연출은 에이스 컴뱃 쪽, 분위기와 설정은 파이널 카운트다운 쪽을 따른다.

**디자인 원칙** (작업 내내 지킨 것)
- 빨강·파랑·초록 3색 대비를 UI 전반에 쓴다.
- 고증을 지키되 재미를 깎지 않는다. 고증이 재미를 죽이면 고증을 조정하고 그 사실을 적어 둔다.
- 화면에 나오는 단위는 소련 기체답게 **km/h · m** 로 통일한다 (강하율만 m/s).
- 연출 변경이 게임 판정을 바꾸면 안 된다. 바꿔야 한다면 의도된 변경임을 명시한다.

## 3. 저장소 · 빌드 · 배포

### 3-A. 공개 링크
게임은 claude.ai 아티팩트 `https://claude.ai/artifact/1LxwE2ryzg7Z6F5S8tEu3j` (slug `02c99a4d-4ecd-4755-9001-7f3d8ce4e7c6`,
**공개**)로 올린다. 새 버전은 같은 아티팩트에 다시 올려 주소를 유지한다 (`publish_files`, `shared_live: public`).
**아티팩트에서는 멀티가 안 된다** (`docs/MULTIPLAYER.md` 2-5). 16 MiB 한도.

### 3-0. 저장소 복원 이력 (2026-11-17) — 먼저 읽을 것
11-16 세션이 끊기면서 원래 저장소(44개 파일 · git 이력)와 검사 하네스가 **둘 다 사라졌다**.
원격이 없었고 하네스는 세션 임시 폴더에 있었기 때문이다. 남은 것은 빌드된 HTML 하나였다.

그 HTML에서 저장소를 **거꾸로 복원**했다 (`tools/extract_from_html.py`).
- 코드 내용은 한 글자도 바뀌지 않았다. `python3 build.py` 결과가 원본 HTML과 **바이트 단위로 같다**
  (sha256 `9dd0d05e…a8e1fc3`).
- 파일 경계는 원본 HTML에 표시가 없어서 **섹션 주석과 이 문서 5절의 파일 지도를 기준으로 다시 나눴다.**
  그래서 파일이 44개가 아니라 JS 52개 · CSS 5개다. 이름은 코드 주석에 남은 원래 이름
  (`00-core`, `32-missiles`, `81-rear-mirror`, `95-intro-logo` …)을 최대한 따랐다.
- 예전 git 이력은 없다. 복원 커밋이 첫 커밋이다.
- 하네스는 새로 짰다 (12절). 예전 하네스의 렌더 검사 스크립트들은 다시 만들지 않았다.

**같은 일이 다시 생기지 않게 GitHub 같은 원격에 반드시 올린다.** 세션 폴더는 영구 저장소가 아니다.

### 폴더
```
src/js/*.js               소스 52개 (12,700줄)
src/css/*.css             5개 (3,128줄)
src/assets/               GLB 모델 · 텍스처 · 티저 영상 · 오프닝 사진 (원본 바이너리)
src/index.template.html   HTML 틀 ({{CSS}} · {{JS}} · {{ASSETS}} 자리표시)
src/manifest.json         JS · CSS · 에셋의 순서와 에셋 id — 빌드 순서는 여기서 정한다
build.py                  이 전부를 HTML 한 개로 합친다
tools/harness/            결정론 회귀 검사 (12절)
tools/extract_from_html.py  빌드된 HTML → src/ 복원 (비상용)
dist/                     빌드 결과 (gitignore 됨)
docs/HANDOVER.md          이 문서
README.md                 짧은 안내
```

### 빌드
```bash
python3 build.py        # → dist/STEEL_TEMPEST_V15_0_0_alpha_6.html (버전은 HTML 안의 "STEEL TEMPEST Vx.y.z" 에서 읽는다)
prettier --write "src/js/*.js" "src/css/*.css"   # 코드 모양 (120자)
```
`src/manifest.json` 의 `js` 순서대로 이어 붙인다 (파일 이름 정렬이 아니다). **순서가 곧 의존성**이다 —
임무 파일은 반드시 `21-campaign.js` 보다 **앞**에 와야 한다. **새 파일을 만들면 manifest 에 넣어야 빌드에 들어간다.** `early` 목록은 인트로 화면 바로 뒤(`{{EARLY_JS}}`)에 들어간다 — THREE · 게임 코드를 쓰면 안 된다.
에셋은 base64(120자 줄바꿈)로 `<script id="asset-...">` 블록에 넣고 런타임에 `readAsset(id)` 로 읽는다.
버전을 올릴 때는 버전 문자열을 전부 바꾼다 (`grep -rn "15\.0\.0" src` — 템플릿 2곳 · `70-input.js` 1곳).

## 4. 절대 깨면 안 되는 규칙

### 4-1. 난수 분리 — 가장 중요
| 함수 | 쓰임 | 규칙 |
|---|---|---|
| `rnd()` | **게임 판정** (명중, 기만, AI 결정, 웨이브) | 연출 코드에서 **절대 호출 금지** |
| `vrnd()` | 눈에 보이는 연출 (불꽃, 연기, 파편) | 자유롭게 |
| `arnd()` | 소리 | 자유롭게 |

연출을 고치다 `rnd()` 를 한 번만 더 당겨도 그 뒤 모든 판정이 어긋난다. 회귀 검사가
이것 때문에 매번 전부 잡아냈다.

**V14.4.1 부터 `rnd` 는 독립 난수 함수다** (`00-core.js`, mulberry32). 예전엔 `rnd = Math.random` 이라
three.js 가 객체를 만들 때(uuid)나 `Math.random` 을 쓰는 연출이 돌 때도 판정 난수열이 밀렸다.
- 시드는 시작할 때 `Math.random` 에서 한 번 받는다. 하네스는 `rnd.seed(n)` 으로 고정하고 `rnd.state()` 로 추적한다.
- 이제 `Math.random` 은 판정과 무관하다. 연출에서 써도 판정은 안 바뀌지만, 새 연출 코드는 `vrnd()` 를 쓴다.
- 기체 대응수단의 플레어 · 채프 퍼짐(`32-missiles.js` `flare()` · `chaff()`)은 시커 시야 판정에 쓰이므로 `rnd()` 가 맞다.

### 4-2. 색은 sRGB로 들어간다
V14.4.0에서 `T.Color.prototype.setHex/setStyle` 을 감싸 **코드에 쓴 16진수를 sRGB로 해석**하게 했다.
- `new T.Color(0xff8800)` · `.set('#f80')` → 자동 변환됨 (그냥 쓰면 된다)
- `.copy()` · `.setRGB()` → **변환 안 됨**. 선형 값이다. HDR 효과(불꽃, 폭발)에 1을 넘는 값을 넣을 때 이걸 쓴다.
- 새 색 텍스처를 만들면 **반드시** `tex.encoding = T.sRGBEncoding` (법선맵·데이터맵은 제외)
- 새 커스텀 셰이더에는 `#include <tonemapping_fragment>` 와 `#include <encodings_fragment>` 를 `gl_FragColor` 뒤에 넣는다

이걸 빠뜨리면 그 부분만 색이 뜨거나 바랜다.

### 4-3. 단위
- 내부 계산: **m/s · m** (바꾸지 말 것)
- 화면 표시: **km/h · m** (`MS2KMH` · `kmh()` 헬퍼)
- 강하율만 m/s
- 월드 스케일: 기체·항모·미사일 전부 **실측 미터 × 3**

### 4-4. 연출 변경은 판정을 바꾸지 않는다
시각 작업을 하면 반드시 하네스를 돌려 모든 시나리오가 **프레임 단위로 동일**한지 확인한다 (12절).
의도적으로 게임성을 바꾼 것은 지금까지 셋뿐이다: 기만 재굴림, MiG 한계 9G, 미사일 유도 개편.

  (V14.4 까지 예광탄이 사실상 안 보였던 이유).

### 비행 물리 개편 — V14.7.0 (`34-flight.js` `phys`)
**문제**: 수직으로 세워도 실속이 안 걸렸다. 측정: 고도 1000 m · 900 km/h 에서 애프터버너로 세우면 1169 km/h 까지
가속하며 22 km 까지 끝없이 올라갔고, 건식 추력으로도 696 km/h 를 유지했다. 원인 넷:
1. 추력이 너무 셌다 — 건식 16 + AB 15 = 31 m/s² (3.2 G). 실기 MiG-29 추중비는 AB 로 약 1.1.
2. 중력의 진행 방향 성분이 0.8 배로 깎여 있었다.
3. 고도 효과가 없었다 — 추력 · 항력 · 실속 속도가 고도와 무관.
4. 실속 처리 버그: 진행 방향에서 y 만 빼고 정규화해서 **수직일 때는 방향이 그대로**였고, 속도가 35 에서 멈춰 계속 떠올랐다.

**고친 것**
- 추력 `P.mig.thr 10 · ab 5` (≈1.0 G · 합 1.5 G), `P.f16.thr 9.4 · ab 4.7` (같은 비율). 항력 계수는 `thr/maxV²` 라 해면 최고속은 그대로.
- 중력 진행 방향 성분 1.0 배 (실제 물리).
- 공기 밀도비 `airDensity(y) = exp(−y/8500)` (미사일과 같은 식): 추력 × 밀도^0.75, 항력 × 밀도, 선회율의 양력 × 밀도,
  **실속 속도 ÷ √밀도** (높이 올라가면 같은 양력에 더 빠른 속도가 필요 — 지시 대기속도 기준 실속).
- **실속 중에는 속도를 벡터로 적분**한다: 중력은 통째로, 양력은 경로 수직 중력 성분의 (속도/실속속도)² 만큼만.
  수직 상승 끝에서 속도가 0 을 지나 꼬리부터 미끄러지고, 받음각 한계가 기수를 끌어내린다 (해머헤드).

**결과** (기수 수직 · 900 km/h 출발)
| 출발 | 실속 | 그 뒤 |
|---|---|---|
| 1000 m · AB | 36초 · 약 8000 m (486 km/h) | 기수가 떨어져 강하 |
| 1000 m · 건식 | 24초 · 약 5300 m | 〃 |
| 5000 m · AB | 23초 · 약 9500 m | 〃 |
저고도에서 AB 로 세우면 한동안 버티고(실기도 추중비 > 1), 건식으로는 반드시 실속한다.

**게임 감각에 미치는 것**: 수평 가속이 예전보다 느리다 (건식 약 60%, AB 약 절반). 항모 발진 직후 AB 를 끄고 기수를 많이
들면 실속한다 — 실기처럼 발진 직후엔 AB 를 유지해야 한다. 고공에서는 선회가 무디다. 하네스 시나리오 `vclimb` 이 이 동작을 지킨다.

## 7. 미사일 유도 (V14.2에서 전면 개편)

예전에는 **락만 걸면 무조건 쫓아갔다.** 지금은 실제 시커처럼 동작한다.

### SARH (R-27R) — 반능동 레이더
- 쏜 쪽 레이더가 **명중할 때까지 락(조사)을 유지**해야 반사파를 따라간다
- 락이 끊기면 마지막 위치·속도로 **2.5초 관성 비행**(`MSL_MEM`), 그 뒤엔 직진
- 그 안에 락을 되찾고 표적이 시커 시야 안에 있으면 다시 문다
- 시커 시야(짐벌) **±50°**

### IR (R-73) — 적외선, 발사 후 망각
- 쏘고 나면 **미사일 자체 시커**로만 쫓는다. 쏜 쪽 IRST 락은 더 필요 없다
- **락 없이도 발사 가능** — 시야 안에서 가장 뜨거운 적을 스스로 찾아 문다
- 시커 시야 **±60°**, 탐지 거리 6 km
- 플레어에 속은 미사일은 **다시 표적을 찾지 않는다**(`m.seduced`)

### 공통
- **비례항법**(PN, 상수 4). 시선이 도는 쪽으로 가속
- **횡가속 제한**: SARH 25 G · IR 40 G. 속도²와 공기밀도에 비례해 줄어든다
  (`mslMaxAcc`: 느리거나 높이 올라가면 못 꺾는다)
- 세게 꺾을수록 속도를 잃는다 (`MSL_IND_DRAG`)
- 발사 후 0.35초는 조종하지 않는다 (기체에서 떨어지는 동안)
- 최고 속도 SARH 800 · IR 700 m/s (원래 640/540이었는데 꼬리 추격이 불가능해 실기값에 맞춰 올림)
- HUD에 날아가는 내 미사일 상태가 뜬다: `ILLUM / MEMORY / LOST / TRACK / SEARCH / DECOYED` + 명중 예상 시간

### 대응수단 (`32-missiles.js`)
- **기만은 살포할 때마다 다시 굴린다.** 예전엔 한 번만 굴려서 미사일의 37%가 절대 안 속았다 (실제 버그였음)
- 확률 `min(0.65, 1 − 0.55^n)` — 네 번 뿌리면 SARH 4%, IR 1% 남음
- 플레어는 **미사일 시커 시야 안**에 있어야 속인다

### 검증 결과 (`msltest.js` — 게임 루프 없이 `updMsl`만 직접 돌림)
- SARH: 락 유지하면 명중, 끊으면 빗나감 (예전 코드는 11 km 고공에서도 다 맞았다)
- IR: 쏘자마자 시커를 꺼도 명중. 락 없이 정면 20° 옆도 찾아 묾. 90° 옆(시야 밖)은 못 찾음
- 적 IR 꼬리 3 km: 플레어 없으면 20/20 피격, 플레어 4번이면 1/20, 7G 선회까지 하면 0/20
- G 제한을 일부러 5 G로 낮추면 9 G 표적을 놓침 → 제한이 실제로 걸린다는 확인

## 10. 성능 — 폰에서 터지던 것들

이 프로젝트에서 가장 오래 싸운 부분이다. 사용자가 폰으로 테스트해서 전부 실제 문제였다.

### 10-1. 텍스처 메모리 (컨텍스트 로스트) — V14.2.1 / V14.2.2
**증상**: "WEBGL CONTEXT LOST" 뜨며 튕김.
**원인**: 모델 텍스처를 **원본 크기로 통째로 펼친 다음** 줄이고 있었다. 4096×4096 한 장이 67 MB인데
여섯 장이 동시에 → 봉우리 **246 MB**.
**해결**: `createImageBitmap` 의 resize로 **목표 크기로 바로** 디코드 (원본이 메모리에 아예 안 올라감).
크기는 PNG/JPEG 머리말에서 숫자만 읽는다. 한 번에 한 장씩만 디코드. 폰은 갑판 1536 · 계기판 1024로 제한.
**결과**: 61.6 → 2.1 메가픽셀, 텍스처 56 → 38 MB.

### 10-2. 화면 효과 층 (하얘지며 튕김) — V14.2.4
**증상**: 구름 들어갈 때 화면이 하얘지더니 튕김.
**원인**: 효과 6개가 **한 요소에 그라데이션 5겹**으로 올라가 CSS 변수로 매 프레임 갱신 →
전체 화면 재래스터. 구름 속 화이트아웃이 켜지는 순간 터졌다.
**해결**: 효과마다 요소를 따로 두고 **불투명도만** 바꾼다(GPU 합성만). 그라데이션은 96×96 캔버스에
한 번만 그려 늘려 붙인다. `backdrop-filter`(매 프레임 화면 되읽기) 제거.

### 10-3. 구름 랙 — V14.2.3

  `image` 를 바꾸므로 그 텍스처를 쓰는 모든 재질이 같이 고쳐진다.
- **조명 확인** (`rgCheckLight`): 회색 표준 재질 + 실제 도색 재질(큰 텍스처 3장)을 **실제 장면의 빛**(해 · 하늘빛 · 환경맵 · 그림자)으로
  그리고, 같은 그림을 조명 없이 그린 기준과 비교. 기준은 밝은데 조명 쪽이 새까마면(두 번 연속 — 0.25초 간격) **안전 단계**를 올린다:
  1 그림자 끔 · 2 환경맵 대신 고른 주변광(`gfxAmb`, 날씨만큼 어둡게 `wxAmbUpdate`) · 3 모든 표준 재질 → 램버트(`rgLambertizeAll`, 장면 · 콕핏 · 템플릿).
  맑은 낮에 해를 정면으로 받는 회색 판이 기준의 30% 도 안 되면(전부 그늘 = 그림자 판정 깨짐)도 올린다.
  단계는 `localStorage.stGfxSafe` 에 기억 — 다음 실행부터 처음부터 적용. **되돌리기: 주소 끝에 `?gfxreset`.**
- 점검 판은 해 쪽 400 단위(그림자 상자 안)에 두고 **점검하는 순간에만 보인다.** 렌더 타깃 encoding 을 화면과 같게 해서 셰이더를 한 벌 더 굽지 않는다.
- **언제**: 로딩 끝(인트로가 기다린다 — 아래) · 출격 1초 뒤 · 컨텍스트 복원(환경맵 다시 굽기 + 텍스처 전부 다시 확인) · 앱/탭으로 돌아옴 · 비행 중 20초마다.
- **로딩 완료 조건 강화**: 인트로 → 표지는 이제 텍스처 **전부** 펼침 + GPU 에 올림 + 점검 통과까지 기다린다(최대 30초, 막대에 '그래픽 점검 중').
  예전엔 먼저 보일 텍스처만 최대 8초 기다려 나머지가 게임 중에 올라왔다.
- **펼치기 경로**: `LOWGPU`(폰 · 터치 기기 · 메모리 4 GB 이하 — 아이패드 프로처럼 `MOBILE` 이 놓치던 기기 포함) 와 `WEBKIT`(사파리 · iOS 전부 —
  ImageBitmap 을 WebGL 로 올리면 검게 나오는 버그가 알려져 있다) 은 펼친 그림을 **캔버스로 옮겨** 올린다. 크기 0 · 새까만 그림은 실패로 보고
  `<img>` 경로로 다시 펼친다 (`texSourceOut`). 크기 줄이기 옵션을 무시하는 브라우저도 여기서 줄인다.
- `RENDER_SAFE` 를 `LOWGPU || WEBKIT || 안전 단계 ≥ 1` 로 넓혔다 (그림자 끄기 방식 · 셰이더 미리 굽기 · 거울 sRGB 를 예전 길로).
- 같이 고친 것: **출격할 때마다 도색 텍스처를 지우던 것**(`disposePlayerModel` — 템플릿 · 주기 기체와 같이 쓰는 텍스처를 지워 GPU 에 다시 올렸다) ·
  **환경맵 굽기 누수**(날씨를 바꿀 때마다 PMREM 렌더 타깃이 남았다 — `envRT`).
- 검증: 하네스 25개 판정 동일. 실시간(SwiftShader): PC · 폰 흉내 · 밤 폭풍 · 컨텍스트 소실 → 오탐 없음(안전 L0 · 복구 0).
  **고장 주입**: ① 가로 1000 넘는 텍스처를 0 으로 올리는 기기 흉내 → 전부 찾아 다시 올림(폰 10회) · ② PBR 셰이더가 새까맣게 나오는 기기 흉내 →
  L1 → L2 → L3 로 올라가 항모 · 기체가 램버트로 정상 표시. 렌더 진단 줄에 `안전 L? · 텍스처 복구 ? · 점검 ?` 가 나온다.

## 11. 설계만 하고 안 만든 것

### 11-1. 보급 관리 시스템
**발상**: 과거로 떨어져 재보급이 불가능하다. 항모 무장 재고를 관리하며 싸운다.
- 워프 이후 캠페인에만 적용 (훈련·자유 모드는 무제한)
- **기총 150발 제한** — **V14.4.2 에서 먼저 넣음. 모든 모드 공통**(훈련 · 자유 · 캠페인, 사용자 결정 2026-11-17).
  `P.mig.gun = 150` 한 곳에서 정한다. 연사 속도는 V14.5.0 에서 **30발/초**(`P.mig.rof`) — 5초면 바닥. 항모 착함 보급은 150까지.
  TR-2 상대 MiG-29 도 150발. (LEGACY 웨이브 격파 공중 보급은 V14.8.0 에서 삭제)
  **피해량**: V14.6.0 에서 **10발 명중이면 F-16 격추**(`P.mig.gunDmg = 0.1`, 사용자 결정). 예전엔 23발이었다.
- 동료기가 쏘는 미사일도 같은 재고에서 나가게 하면, "동료를 믿고 맡길까 / 내가 아껴 쏠까"라는
  선택이 매 판 생긴다 (윙맨 시스템과 묶이는 지점)

### 11-2. 윙맨 · 흩어진 동료 시스템
**설정**: 시공 폭풍에 휩쓸릴 때 항모에 도달하지 못하고 튕겨져 나온 아군이 과거 곳곳에 흩어져 있다.
임무 중에 찾아 합류시킨다. 합류 시 연료·무장이 바닥난 상태로 나타나면 항모까지 호위해야 한다.

**조작**: 키 하나로 명령 3개 — **공격**(내 락 표적을 침) · **엄호**(내 꼬리의 적을 뗌) · **복귀**(편대 자리로).
오른쪽 뒤 150 m에 붙고, 선회하면 바깥쪽으로 돌아 자리를 지킨다.
실력은 "도와주는 정도"로 — 혼자 쓸어버리면 플레이어가 할 게 없다. 성격은 무전 말투로 구분.

**결정됨**: 동료 3~4명. 배신 반전은 **루트별로 다르게**.
**미결**: ① 동료 격추 시 영구 사망인가, 아니면 이탈→수리인가 ② 한 출격에 편대 최대 몇 기인가(2기 / 4기)

**만들 때 주의할 버그 4가지** (지금 코드 구조상 반드시 생긴다)
| 버그 | 원인 |
|---|---|
| 허공에서 스폰 | 지금 기체 생성 함수는 전부 공중 좌표에 바로 꽂는다. 갑판 발진이나 화면 밖 합류로 해야 한다 |
| 갑자기 사라짐 | 격추·종료 시 한 프레임에 목록에서 지운다. 이탈 기동을 보여주고 시야 밖에서 지워야 한다 |
| 편대 유지 안 함 | 지금 AI는 무조건 `p`(플레이어)를 적으로 본다. 편대 위치 추종을 따로 짜야 한다 |
| 제자리 선회 반복 | 적 AI는 할 일 없으면 10초마다 방향을 새로 잡는다. 윙맨에 쓰면 빙글빙글 돈다 |

### 11-3. 피격 생존 굴림 · 조종사 사출
사용자가 마지막에 제시한 설계. **피격 판정이 뜨는 즉시** 판단:
1. **미사일 종류** — 열추적이면 생존률 ↑, 레이더면 ↓
   (고증 근거: R-73은 탄두가 작고 배기구를 쫓아 뒤를 때린다. R-27R은 탄두가 크고 근접신관이라 동체 옆에서 터진다)
2. **피격 부위** — 후방일수록 사망률 최소, 앞으로 갈수록 상승
3. **생존** → 폭발 후 연기 뿜으며 하강 + **조종사 사출**
4. **사망** → 그냥 폭발 후 하강

**미결**: ① 기총 피격에도 적용하나 ② 적기만인가 플레이어도인가 ③ 지금 체력 체계(맞을 때마다 깎임)와
어떻게 맞물리나 — 체력 0이 되는 한 방에만 굴릴지, 체력을 없애고 매 피격마다 굴릴지

사출된 조종사는 **흩어진 동료 시스템과 바로 이어진다** (적이면 포로, 아군이면 구조 대상).
둘을 같이 설계하는 게 좋다.

## 12. 검사 하네스 — 이게 이 프로젝트의 핵심 도구다

위치: `tools/harness/` (**저장소 안**. 예전처럼 임시 폴더에 두지 말 것). 2026-11-17 새로 짰다.
필요한 것: `pip install playwright`, 크롬(`CHROME` 환경변수, 기본 `/usr/bin/google-chrome`), 인터넷(three.js CDN).

### 쓰는 법
```bash
python3 build.py
python3 tools/harness/run.py run dist/STEEL_TEMPEST_V15_0_0_alpha_6.html /tmp/new.json      # 시나리오 전부 (약 1분)
python3 tools/harness/run.py diff tools/harness/baseline/V14_8_0.json /tmp/new.json  # 프레임 단위 비교
python3 tools/harness/run.py run <html> <out.json> carrier tr1 --shots /tmp/shots   # 일부만 + 마지막 화면 저장
python3 tools/harness/run.py fxcheck /tmp/new.json   # 비행 효과 ON/OFF · 콕핏/외부 시점이 판정을 바꾸는지
```
`diff` 는 시나리오마다 `동일` 또는 `처음 갈라진 프레임 · 그때 해시/난수 호출 수 · 마지막 상태 차이`를 보여 준다.
연출만 바꿨는데 `다름`이 나오면 연출 코드가 판정을 건드린 것이다.

### 구조
| 파일 | 하는 일 |
|---|---|
| `det.js` | 게임보다 먼저 주입. `Math.random` 을 시드 난수로, `performance.now` · `requestAnimationFrame` 을 가짜 시계로 바꾼다. 프레임은 `__det.step()` 을 불러야만 돈다. 키 입력도 정해진 프레임에 넣는다 |

| `baseline/V15_0_0_a3_su33.json` | alpha.3 에 더한 시나리오 6개의 기준. `run ... su33-carrier su33-vclimb su33-trap su33-cobra multilock loadout-trap` 결과와 `diff` |

| `baseline/V14_5_0.json` | 기총 10발 · 탄 속도 이전 기준 (시나리오 14개) |

### 결정론을 지키려고 한 것 (만들면서 실제로 걸린 것들)
- **모델 로딩이 끝날 때까지 기다린 뒤 출격한다.** 로딩 도중에 출격하면 결과가 달라진다(기체 생성이 모델 유무를 탄다).
- **출격(`start()`)은 첫 프레임 안에서 한다.** `init()` 이 판정 난수를 당긴다.
- **프레임 사이에 `rnd` 상태가 바뀌면 `ERRORS` 로 찍는다** (V14.4.1+, `rnd.state()` 비교).
- **프레임 밖에서 불린 `Math.random` 은 별도 난수열로 돌린다** (V14.4.0 처럼 `rnd = Math.random` 인 빌드용). 텍스처 업로드처럼 실제 시간에 맞춰 도는 비동기 콜백에서
  three.js 가 uuid 를 만들며 `Math.random` 을 당기는데, 게임의 `rnd` 가 바로 `Math.random` 이라 판정 난수열이 밀렸다.
  게임 코드가 프레임 밖에서 난수를 당기면 결과에 `ERRORS` 로 찍힌다.
